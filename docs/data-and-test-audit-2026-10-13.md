# 数据与测试边界审查（2026-10-13）

本报告对应请求的第 3 项，以下建议尚未实施。日期默认值和 Food2050 迁移问题的修复及其专用回归检查属于第 1、2 项。

结论：当前检查对「合法的空数据」偏严格，对「抓取失败、不完整数据和错误数值」却偏宽松。建议明确数据状态，再补行为测试；不建议直接放宽或继续堆叠固定断言。

## 1. 高优先级：发布检查没有分来源健康度，也没有日期新鲜度

位置：`scripts/verify-menu-data.py:32`、`menu.py:_curl` / `_load_uzh_weekly`。

证据：下载线上 `data.json`，其构建日期为 `2026-10-12`；10 月 13 日有 75 道 ETH 菜、0 道 UZH 菜。把原始文件送入 `validate_payload`，仍然通过。检查只要求活跃日有任意菜，ETH 正常便能掩盖 UZH 全部失效。

建议：

- 构建时记录每个来源的抓取成功、明确无供应、请求失败、解析失败等状态，不能一律变成空数组。
- 发布时检查构建日期是否等于 Europe/Zurich 当天，分别检查 ETH / UZH 来源状态；保留 32 家食堂的名册要求。
- 对确认的节假日和闭店允许空菜单；对来源失联或结构变化失败并保留可诊断日志。先记录近期正常覆盖率，再设计数量异常阈值，避免要求每家每天必须有菜。

验证建议：ETH 正常 + UZH 404、HTTP 200 但格式变化、来源明确发布空菜单、旧构建日期四组输入必须得到不同结果。

## 2. 高优先级：预加载窗口只有构建当天接受校验

位置：`scripts/verify-menu-data.py:44`。

证据：把下载文件中 `days['2026-10-13'].mensas` 改成 `[{'wrong': true}]`，保留构建当天不变，检查仍通过。日期、价格、照片、营养值及 `availableDates` 的一致性也没有完整校验。

建议：校验整个 `days` 窗口的结构、32 个稳定且唯一的 ID、两个 meal slot、非空菜名、营养/价格的有限数值以及日期索引一致性。不要要求未来日必须有菜、照片或营养数据；未发布、周末和未来照片缺失是合法情况。

验证建议：正常未来空日应通过；未来日结构损坏、重复 ID、索引包含不存在日期、非有限数值应失败。以结果为断言，不仅断言「未抛异常」。

## 3. 高优先级：零值被当成缺失，非有限数值反而被接受

位置：`menu.py:_num` / `_keep_number`。

实际调用结果：

| 输入 | 当前结果 |
| --- | --- |
| `0` / `'0'` | `None`，字段被丢弃 |
| `-1` | `-1.0` |
| `'NaN'` | `nan` |
| `'Infinity'` | `inf` |

合法的「盐 0 g」「糖 0 g」会显示成无数据；非有限浮点数可被 Python 输出成浏览器 JSON 解析不能接受的值。

建议：通用数值解析保留有限的零值，用 `None` 表示缺失；负值、单位和合理范围在价格/营养各自边界校验。对 ETH 若已确认零值是来源的缺失哨兵，单独在 ETH 适配器表达，不要应用到所有来源。序列化最终数据时禁止 NaN/Infinity。

验证建议：零值、数字字符串、空字符串、None、逗号小数、非有限值和负值分别测试；保留真实零值与来源哨兵的区别。

## 4. 中优先级：工作日全部空菜单会阻断合法的闭店更新

位置：`scripts/verify-menu-data.py:82`、`.github/workflows/menu.yml` 的 `allow_empty_today`。

证据：保留 32 家食堂、清空周一所有 meal slot，会被拒绝，即使来源明确发布的是闭店信息。手动开关能处理已知假日，但无人干预的节假日仍会保留旧构建。

建议：维持「来源失败不能发布」的原则，把「确认闭店」与「抓取不到」分开。已确认的校历/来源闭店状态可允许正常空日；手动开关作为例外处理，而不是主要机制。前端应能区别未发布、闭店、来源故障。

不要简单删除工作日空数据检查：这会再次把服务中断伪装成正常空菜单。

## 5. 中优先级：两项显示设置读取但没有保存

位置：`template/app.js:loadPrefs` / `savePrefs`。

证据：把 `prefs.openingTimes` 与 `prefs.prices` 设为 `false` 并调用真实的 `savePrefs`，保存 JSON 的字段只有 `meal, selected, photos, theme, customGroups, collapsedMensas`。重新打开页面时营业时间和价格回到默认开启。

建议：在同一个持久化入口保存这两项；添加关闭 → 保存 → 重新打开的行为测试。不要添加另一套同步函数或绕过 `renderAll`。

## 6. 中优先级：来源已有饱和脂肪，UZH 映射却没有读取

位置：`menu.py:UZH_NUTRIENT_MAP`。

证据：10 月 13 日 Garden 的公开详情响应包含 `dish.stats.saturatedFat.amountPer100g` 和 `amount`，现有映射没有对应 `saturated`，表格该行一直空着。

建议：核实来源字段/单位后，在唯一营养映射添加 `saturatedFat → saturated`，以真实详情样本验证每 100 g 和每份值。缺失该字段的菜仍保留空数据。

## 测试策略建议

原仓库主要靠动画源码文本检查和当天数据检查，没有覆盖菜单抓取及日期行为的运行测试。源码检查适合拦住明确禁止的写法，但不能证明快速切换、缺失数据和中断动画时的结果正确。

这次仅为已修复的两项增加 `scripts/test-menu.py`（精简真实 Food2050 响应）和 `scripts/test-date.cjs`（真实初始化/数据入口与固定时钟）。它们不依赖网络，并在部署工作流中运行。

后续建议：

1. 为上述六项各补一个会先失败的行为回归测试，然后再修改对应行为。
2. 用正常供餐、合法空日、接口失败、部分字段缺失四类 fixture 覆盖来源边界。不要只测试空对象。
3. 增加少量真实浏览器测试，断言跨日选择、日历选中态、显示设置重载，以及连续快速切换后节点复用和最终布局；降低动态效果测试的时序依赖。
4. 真实网络冒烟检查与离线单元测试分开。网络检查关注来源结构和日期，不把某道菜、照片数量或固定每日菜数写成永久断言。

以上建议均未改动对应生产行为。
